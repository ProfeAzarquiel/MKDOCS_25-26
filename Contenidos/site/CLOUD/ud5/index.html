    ¿QUE ES UN ORQUESTADOR?

    Un orquestador, es una herramienta de software que automatiza el despliegue, la gestión, el escalado, la red y el ciclo de vida de aplicaciones empaquetadas en contenedores.

    Mientras que una herramienta como Docker te permite ejecutar un contenedor en una sola máquina, el orquestador coordina cientos o miles de contenedores repartidos en múltiples servidores o nodos (formando un clúster).

    PRINCIPALES FUNCIONES:

    • Programación de la ubicación (Scheduling): Decide en qué servidor físico o virtual debe ejecutarse cada contenedor según los recursos disponibles (memoria, CPU).
    • Escalado automático: Aumenta o disminuye el número de réplicas de un contenedor según la demanda de tráfico.
    • Autoreparación: Si un contenedor o un servidor completo falla, lo detecta y levanta una nueva instancia en otro servidor de forma automática.
    • Balanceo de carga: Distribuye el tráfico de red entre los distintos contenedores y les permite comunicarse entre sí de forma segura sin importar dónde estén ubicados físicamente.
    • Actualizaciones y reversiones (Rolling updates): Permite actualizar las versiones de una aplicación poco a poco, sin interrumpir el servicio, y dar marcha atrás si algo sale mal.

    Algunos de los orquestadores más conocidos son:

    • Kubernetes: es el estándar de la industria y el orquestador de código abierto más utilizado..
    • Docker Swarm: es el motor de orquestación nativo del ecosistema Docker, que viene integrado con sus instalación.
    • Amazon ECS / EKS: son los servicios de orquestación administrados que ofrece Amazon Web Services (AWS).

    KUBERNETES

    Es una plataforma de código abierto que sirve para automatizar la implementación, escalado y operación de aplicaciones con contenedores. Desarrollado por Google y luego liberado como código abierto en 2014, actualmente es uno de los proyectos más populares de la Cloud Native Computing Foundation (CNCF). Ya que se ha convertido en la plataforma de orquestación de contenedores más utilizada y ampliamente adoptada por empresas de todo el mundo.

    Kubernetes crea una capa de abstracción entre la infraestructura y las aplicaciones. Por ejemplo, teníendo múltiples servidores, te permite agruparlos en lo que llamariamos clúster y consumirlo como una pieza individual, permitiendo desplegar aplicaciones sobre todos los nodos del clúster de una forma transparente para el usuario.

    Por ejemplo, en un entorno tradicional un administrador de sistemas tendría que provisionar una máquina virtual (con sus configuraciones de red, paquetería, hardware, etc) por cada aplicación.

    Mientras que en un entorno de Kubernetes, el administrador solo tiene que añadir y mantener los nodos del cluster, de modo que cuando se solicita una nueva aplicación, se le asigna una reserva lógica de recursos del cluster. Es decir, no le asignamos una "máquina" sino un numéro de recursos cuatificados en CPU y RAM, que no tienen por que estar en un nodo en concreto.

    En resumen, Kubernetes nos aporta:

    • Automatización de tareas y simplicación de la operativa.
    • Escalabilidad en función de la demanda (Contenedores ó Nodos).
    • Resiliencia ante errores o caídas.
    • Estandarización entre diferentes entornos (migraciones).
    • Ecosistemas de servicios y funcionalidades.

    Oportunidades laborales

    Kubernetes es una tecnología muy demandada en el mercado laboral, por lo que tener conocimientos en Kubernetes puede abrirte muchas puertas en tu carrera profesional ya sea como especialista DevOps, Administrador de Sistemas o especialista en seguridad.

    ARQUITECTURA DE KUBERNETES

    Todo clúster gestionado con Kubernetes consta de dos piezas fundamentales:

    El "control plane" o nodo maestro: responsable de gestionar al resto de nodos del clúster. No ejecuta pods ni ningún tipo de carga de trabajo, solo se limita a interactuar con el resto de nodos y gestionar los recursos del clúster.

    Los "workers" o nodos de trabajo alojan los pods (contenedores) y las cargas de trabajo, es decir, son los encargados de ejecutar las aplicaciones y servicios que se despliegan en el clúster.

    COMPONENTES BÁSICOS DE CUALQUIER NODO

    CONTAINER RUNTIME: es el software que se encarga de ejecutar los contenedores. Docker es el más popular, pero en Kubernetes lo más habitual es usar containerd o CRI-O, versiones más ligeras y especializadas es este tipo de entornos.

    KUBELET: es el encargado de gestionar los contenedores en un nodo y de garantizar que estos se mantengan en el estado deseado. Se comunica con el API Server para recibir instrucciones y transmitirlas al runtime de contenedores.

    KUBE-PROXY: gestiona el tráfico de red en el nodo. Se encarga de enrutar las peticiones a los servicios y de balancear la carga entre los pods. También se encarga de la exposición de los servicios al exterior. Traduce las necesidades de red de los servicios a reglas de iptables de forma automática.

    COMPONENTES ESPECÍFICOS DEL NODO MAESTRO

    KUBE-APISERVER: es el punto de entrada al clúster. Es el componente que recibe las peticiones de los usuarios y de los nodos de trabajo. Es el único que se comunica directamente con la base de datos de Kubernetes, etcd. Almacena el estado del clúster, gestiona las peticiones y las transforma en acciones.

    KUBE-SCHEDULER: es el encargado de decidir en qué nodo se ejecutará un pod. Se basa en las necesidades de los pods y en las capacidades de los nodos para tomar la decisión.

    ETCD: es la base de datos de Kubernetes. Almacena el estado del clúster y es el único componente que almacena información de forma persistente. Es altamente consistente y tolerante a fallos.

    KUBE-CONTROLLER-MANAGER: es el componente que se encarga de gestionar los controladores de Kubernetes. Los controladores son procesos que se ejecutan de forma continua y que se encargan de mantener el estado deseado del clúster. Por ejemplo, el controlador de replicación se encarga de mantener el número de réplicas de un pod en el estado deseado.

    CLOUD-CONTROLLER-MANAGER: es como el kube-controller-manager pero para entornos en la nube. Se encarga de interactuar con los servicios del proveedor, como los volúmenes de almacenamiento, balanceadores de carga, etc.

    En resumen, el api de kubernetes gestiona todas las peticiones de los usuarios o de los nodos y el scheduler decide donde se ejecutan los pods. Mientras que el controlador mantiene el estado deseado del clúster y el etcd almacena el estado del clúster.

    INSTALACIÓN DE KUBERNETES

    Existen varias formas mediante las cuales podemos instalar Kubernetes, dependiendo de que para que finalidad vayamos a usarlo. Principalmente, distinguiremos el uso en entornos de desarrollo y en entornos de producción.

    • Desarrollo: para crear de forma rápida entornos de prueba o laboratorios de prácticas ligeros, existen varias alternativas como MiniKube, Kind o a través de Docker Desktop.

    • Producción: por un lado, podemos crear un cluster Kubernetes mediante la herramienta oficial Kubeadm (K8s), la cual requiere que instalemos manualmente todos los recursos necesarios y puede ser una tarea compleja, sobretodo la primera vez que se hace. Incluso, si tenemos una infraestrucura no muy grande con un número reducido de nodos (por ejemplo, entre 5 y 20), podemos optar por usar la opción de K3s (Kubernetes Ligero).

      Y por otro lado, la forma más recomendada para un entorno de producción profesional, que es contratando servicios en la nube como Amazon EKS o Google GKE; que aunque conllevan un coste añadido, facilita mucho las cosas ya que el proveedor gestiona el plano de control por nosotros.

    Como hemos comentado antes, Kubeadm es la herramienta oficial de Kubernetes diseñada para facilitar la creación, inicialización y configuración rápida de clústeres de Kubernetes estándar, sobre máquinas físicas o virtuales. En el siguiente enlace podemos ver un tutorial bastante completo sobre como crear un laboratorio práctico de Kubernetes con 3 máquinas virtuales Ubuntu (1 Nodo Maestro y 2 Nodos Trabajadores). Sin embargo, nosotros seguiremos el resumen de pasos que tenemos a continuación:

    A EJECUTAR EN TODOS LOS NODOS DEL CLÚSTER

    Hasta que se indique lo contrario, todos los siguientes comandos se ejecutan como root, para actualizar repositorio de paquetes, instalar requisitos previos, desactivar el swap, cargar módulos necesarios y configuración sysctl:

    sudo su

apt update && apt upgrade -y
apt install curl apt-transport-https git wget software-properties-common lsb-release ca-certificates socat -y

swapoff -a
sed -i '/swap/s/^\(.*\)$/#\1/g' /etc/fstab

modprobe overlay
modprobe br_netfilter

cat << EOF | tee /etc/sysctl.d/kubernetes.conf
net.bridge.bridge-nf-call-ip6tables = 1
net.bridge.bridge-nf-call-iptables = 1
net.ipv4.ip_forward = 1
EOF

sysctl --system

    Instalar las claves gpg de Docker para luego instalar y configurar containerd para que use cgroups:

    sudo install -m 0755 -d /etc/apt/keyrings

curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg

echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

apt update && apt install containerd.io -y

containerd config default | tee /etc/containerd/config.toml

sed -e's/SystemdCgroup = false/SystemdCgroup = true/g' -i /etc/containerd/config.toml

systemctl restart containerd

    Instalar claves gpg de Kubernetes, añadir el repositorio (cambiar la versión si es necesario) e instalar kubeadm, kubelet y kubectl:

    curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.30/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg

echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.30/deb/ /" | sudo tee /etc/apt/sources.list.d/kubernetes.list

apt update

apt install -y kubeadm=1.30.1-1.1 kubelet=1.30.1-1.1 kubectl=1.30.1-1.1

apt-mark hold kubelet kubeadm kubectl

    Editamos el fichero /etc/hosts, para añadir el nombre del nodo maestro al DNS local, de modo que sea alcanzable por su hostname (en este ejemplo el hostname sería k8scp):

    echo "<Dirección_IP_Maestro> k8scp" >> /etc/hosts

    A EJECUTAR SOLO EN EL NODO MAESTRO

    Iniciar el cluster con kubeadm (importante cambiar el rango de IPs para pods por uno que no esté en uso en tu red, evitar también el rango 10.XXX.XXX.XXX ya que es un rango reservado para redes privadas). Por último, añadimos el nombre del nodo maestro (recuerda usar el de antes) y el puerto 6443:

    kubeadm init --pod-network-cidr=<rango de IPs para pods> --control-plane-endpoint=<Nombre añañadido en el /etc/hosts>:6443

# EJEMPLO: kubeadm init --pod-network-cidr=192.168.0.0/16 --control-plane-endpoint=k8scp:6443

    ¡¡IMPORTANTE!!

    La salida del comando anterior nos mostrará una serie de datos, incluyendo un comando kubeadm join que luego tendremos que ejecutar en los nodos workers para unirlos al cluster.

echo "deb [signed-by=/usr/share/keyrings/helm.gpg] https://packages.buildkite.com/helm-linux/helm-debian/any/ any main" | sudo tee /etc/apt/sources.list.d/helm-stable-debian.list

    Instalar Helm (necesario para instalar algunas aplicaciones en Kubernetes) y Cilium (nos permitirá conectar los pods entre sí):

    sudo apt update

sudo apt install helm -y

helm repo add cilium https://helm.cilium.io/

helm repo update

helm template cilium cilium/cilium --version 1.16.1 --namespace kube-system > cilium.yaml

kubectl apply -f cilium.yaml

    UNIR TODOS LOS NODOS AL CLUSTER

    En cada uno de los nodos worker pegamos el comando que nos devolvio la instrucción kubeadm init lanzar el siguiente comando:

        kubeadm join <hostname_nodo_maestro>:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>

    Si por algún motivo, no copiamos ese comando o no conocemos algunos de los datos necesarios, podemos ejecutar lo siguiente en el Nodo Maestro para conseguir la información:

    • Para ver el token o si fuera necesario, crear uno nuevo:

      kubeadm token list
kubeadm token create

    • Para ver el hash:

      openssl x509 -pubkey -in /etc/kubernetes/pki/ca.crt | openssl rsa -pubin -outform der 2>/dev/null | openssl dgst -sha256 -hex | sed 's/^.* //'

    Por último, comprobamos que los nodos se han añadido correctamente, ejecutando el siguiente comando en el nodo Maestro:

    kubectl get nodes

    K3s es una distribución certificada, ligera y de alto rendimiento de Kubernetes. Fue creada por Rancher Labs (hoy parte de SUSE) y es un proyecto graduado en la CNCF (Cloud Native Computing Foundation). Además de ofrecer una instalación muy rápida, tiene un tamaño reducido (alrededor de 100 MB), bajo consumo de recursos, es 100% compatible con las APIs y herraminetas de Kubernetes estándar. Su instalación es muy sencilla, como vemos a continuación:

    Configurar el nodo Maestro (control-plane)

    Script para descargar el binario de K3s, configurar el servicio k3s en systemd e iniciarlo automáticamente:

    Si algo va mal durante la instalación de K3S o en la creación del clúster, podemos desinstalar K3s de un nodo, con el comando: /usr/local/bin/k3s-uninstall.sh

    Configurar el archivo kubeconfig:

    Siguiendo con el nodo maestro, si queremos usar kubectl sin tener que escribir sudo delante de cada instrucción, puedes configurar el archivo de kubeconfig para tu usuario, de la siguiente manera:

    Configura privilegios kubectl para tu usuario:
    mkdir -p ~/.kube

sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config

sudo chown $(id -u):$(id -g) ~/.kube/config

export KUBECONFIG=~/.kube/config
    Configurar los nodos Agentes (Workers):

    Para conectar más máquinas a nuestro clúster como nodos trabajadores (workers), necesitaremos dos datos del nodo Maestro:

    • La dirección IP: podemos verla con el comando ip a.
    • El token del nodo: se encuentra en la ruta sudo cat /var/lib/rancher/k3s/server/node-token.

    Una vez que recopilemos esta información, simplemente tenemos que ejecutar el siguiente comando (sustituyendo con los valores que correspondan) en cada uno de los agentes:

    curl -sfL https://get.k3s.io | K3S_URL=https://<IP-DEL-MASTER>:6443 K3S_TOKEN=<TOKEN-DEL-MASTER> sh -

    Kind (Kubernetes in Docker) es una herramienta de código abierto que permite ejecutar clústeres locales de Kubernetes utilizando contenedores de Docker como si fueran los nodos del clúster. Fue desarrollada originalmente para probar el propio código fuente de Kubernetes, pero hoy en día es muy popular entre desarrolladores y equipos de DevOps para reproducir entornos en local o crear laboratorios prácticos. Al basarse en contenedores, es una opción muy ligera y rápida, cuenta con soporte multinodo (incluyendo sus diferentes roles) y está certificado por la CNCF.

    Para instalarlo, partimos de una máquina Ubuntu en la que tenemos previamente instalado Docker. Y vamos a descargar el binario de Kind y a colocarlo en un directorios accesible desde $PATH:

    curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.10.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin
kind version

    Por otro lado, instalamos la utilidad kubectl que es el cliente usado para interactuar con nuestro clúster Kubernetes:

    curl -Lo ./kubectl "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
chmod +x ./kubectl
sudo mv ./kubectl /usr/local/bin
kubectl version --client

    Con estos simples pasos, ya podemos empezar a definir nuestro cluster Kubernetes con Kind.

    PRÁCTICA: CREACIÓN DE UN CLUSTER CON KIND:

    • PERSONALIZAR LA RED VIRTUAL DEL CLUSTER

    Cuando levantamos un cluster con KIND, este crea una red Bridge llamada kind con un direccionamiento por defecto. Para que ese direccionamiento no se solape o interfiera en los direccionamientos que ya tenemos en uso, vamos a crear nosotros esa red con los parámetros que queramos:

    docker network create --subnet 192.168.0.0/24 --gateway 192.168.0.1 kind
    • CREAR FICHERO DE CONFIGURACIÓN DEL CLUSTER:

    Por otro lado, podemos personalizar las características que tendrá nuestro cluster mediante el fichero config.yaml, como el nombre del cluster, el número de nodos, el rol de cada nodo, mapeado de puertos, direccionamiento de los pods y servicios, almacenamiento persistente, etc. Un ejemplo sencillo de un cluster con 4 nodos, puede ser:

    nano config.yaml 
    kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: cpd
nodes:
- role: control-plane
- role: worker
- role: worker
- role: worker
    • LEVANTAR EL CLUSTER:

    Por último, solo tenemos que crear nuestro cluster con el siguiente comando:

    kind create cluster --config=config.yaml

    Credenciales de Acceso al Cluster

    Podemos comprobar que cuando se crea un cluster, se crea también el fichero de configuración con nuestras credenciales para el acceso en ~/.kube/config.

    Comprobaremos que se han creado tantos contenedores como nodos habiamos indicado en el fichero de configuración:

    docker ps

    Y si todo ha ido bien, podemos usar la funcionalidad kubectl para confirmar que todos los nodos están en estado "Ready":

    kind get clusters
kubectl get nodes

    TIPOS DE OBJETOS KUBERNETES

    Un objeto o recurso, es cualquier cosa que podemos definir en un cluster de kubernetes. Cada objeto es de un tipo concreto y tiene unas propiedades y atributos que lo definen. Para definir un objeto, se hace mediante archivos manifiesto que se aplican al cluster para que se crear o modificar recursos. Estos manifiestos pueden ser escritos en formato YAML o JSON, y los principales objetos que podemos definir son:

    POD: es el recurso más básico que podemos crear en Kubernetes, generalmente compuesto por un contenedor (o varios). No es habitual crear pods manualmente, si no a partir de un objeto "Deployment".

    DEPLOYMENT: generalmente se utilizan para definir aplicaciones compuestas por varios "Pods" y las características específicas de cada uno.

    SERVICE: permite exponer los pods o aplicaciones para que se accede desde fuera del cluster.

    VOLUME: usado para persistir información de uno o varios pods.

    NAMESPACE: permite agrupar una serie de recursos en diferentes espacios lógicos separados, dentro del mismo cluster.

    LOS MANIFIESTOS .YAML

    En el archivo .yaml del objeto que queramos crear, obligatoriamente debemos indicar (como mínimo) los siguientes apartados:

    • apiVersion: versión de la API de Kubernetes que se va a usar.
    • kind: tipo de objeto que quieres crear.
    • metadata: datos que identifican unívocamente al objeto (name, uid, namespace...).
    • spec: características específicas del objeto (contendores, volumenes...).

    Por otro lado, es importante destacar que podemos crear varios objetos diferentes usando un único manifiesto.yaml, simplemente deben ir separados por un triple guión ---.

    PODS

    Como ya mencionamos, un pod es el recurso más básico de Kubernetes y aunque lo más común es crearlos a través de manifiestos de mayor nivel, como un Deployment; también es posible crear pods individualmente de las siguientes formas:

    CON KUBECTL

    Los principales gestores y orquestadores de contenedores, estan basados en el mismo estandar OCI (Open Container Initiative), es por ello que podemos usar cualquier imágen descargada de Docker Hub, para crear un Pod en Kubernetes:

    kubectl run mypod1 --image=nginx

    CON UN MANIFIESTO

    No obstante, como ya hemos comentado, en Kubernetes lo normal es definir los recursos mediante manifiestos. Por lo tanto, un ejemplo para crear un Pod igual que el anterior a través de un fichero pod.yaml, sería el siguiente:

    apiVersion: v1
kind: Pod
metadata:
    name: mypod2
spec:
    containers:
      - name: webproxy
        image: nginx

    Luego creamos el Pod mediante el comando:

    kubectl apply -f pod.yaml

    Una vez que hemos creado un recurso mediante un manifiesto, podemos modificarlo sin necesidad de pararlo. Simplemente editando su manifiesto y volviendo a ejecutar kubectl apply. Por ejemplo:

    kubectl exec nginx -- cat /etc/os-release
nano nginx.yaml

#  Modificamos la imagen por "image: nginx:alpine"

kubectl apply -f pod.yaml
kubectl exec nginx -- cat /etc/os-release

    Como vemos, con la instrucción kubectl exec <nombre_pod> -- <comando> podemos ejecutar ordenes dentro de un pod.

    También, usando la instrucción kubectl describe pod <nombre_pod> podemos ver información detalla de un pod, como la imagen usada, en que nodos del cluster se está ejecutando o un histórico de eventos, entre otros.

    Por último, podemos borrar un pod usando la instrucción kubectl delete pod <nombre_pod>.

    NAMESPACE y CONTEXTO

    Los namespaces son una forma de agrupar los recursos de kubernetes. Esto permite que podamos gestionar los diferentes recursos de una aplicación ( pod, deployment, service, etc) para establecer unas cuotas recursos, políticas de seguridad y configuraciones específicas.

    Por defecto, existen cuatro namespaces que usa Kubernetes, que no debemos tocar. Para listar los namespaces creados en nuestro cluster, mostrando sus etiquetas (opción que nos puede ser muy útil más adelante) podemos usar:

    kubectl get ns --show-labels

    Al igual que pasaba con los pods, podemos crear namespaces por línea de comandos con kubectl create ns <nombre_namespace>; o mediante un manifiesto con la opción kubectl create -f <nombre_fichero>. Un ejemplo muy simple de manifiesto para un namespace sería:

    apiVersion: v1
kind: Namespace
metadata:
name: desarrollo
labels:
    name: desarrollo

    Para ejecutar comandos dentro de un namespace, usaremos la instrucción:

    kubectl --namespace desarrollo get pods

    Sin embargo, salvo que queramos lanzar un comando puntual, lo que se suele hacer es asociar el namespace donde queremos trabajar al contexto actual. Un contexto Kubernetes define la configuración de acceso a un cluster específico, incluyendo el nombre del cluster, nombre de usuario y namespace predeterminado. Podemos ver nuestro contexto actual mediante el comando:

    kubectl config view

    Como por defecto, usamos el namespace "default", vemos que no se indica ningún namespace. Pero podemos asignar el namespace que queramos al contexto activo, usando:

    kubectl config set-context --current --namespace=<nombre_namespace>

    Para volver al namespace por defecto: kubectl config set-context --current --namespace=default

    Es importante remarcar que un namespace no es una barrera de seguridad, sino una forma de organizar y gestionar los recursos de forma agrupada. Para aislar recursos de forma segura, debemos usar Network Policies y RBAC.

    DEPLOYMENT y REPLICASET

    Los Deployments son elementos de configuración que permiten la creación de una aplicación de una sola instancia. El deployment gestiona uno o varios objetos replicaset y estos a su vez gestionan uno o más pods.

    Un ReplicaSet es un objeto Kubernetes que asegura que un número específico de réplicas de un pod estén ejecutándose en todo momento. Los deployments utilizan este recurso para gestionar la creación, actualización y eliminación de pods; asegurando la alta disponibilidad y escalabilidad.

    PRÁCTICA 1: MI PRIMER DESPLIEGUE CON KUBERNETES

    A) CREACIÓN Y LANZAMIENTO DEL DEPLOYMENT

    deploy1.yaml 
    apiVersion: apps/v1
kind: Deployment
metadata:
  annotations:
    kubernetes.io/change-cause: "Despliegue nginx:1.21"
  name: first-deployment-gx
  labels:
    app: mi-app-gx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: web
        image: nginx:1.21
        ports:
        - containerPort: 80
    Creamos el manifiesto para el despliegue:
    nano deploy1.yaml

    Aplicamos el manifiesto en nuestro clúster:
    kubectl apply -f deploy1.yaml
    Verificamos que se ha creado el deployment y el replicaset:
    kubectl get deploy
kubectl get rs
    Verificamos que se han creado las 3 replicas de nuestro pod y están en ejecución:
    kubectl get pods
    Verificamos la versión de la imagen usada en los pods (debemos ver la 1.21):
    kubectl describe pod | grep Image

    EN CASO DE CAIDA DE UN POD

    Vamos a comprobar que tanto la redundancia, como la configuración de nuestro Replicaset, funcionan correctamente. Para ello, eliminaremos uno de los pods que estan en ejecución veremos como el Replicaset vuelve a crearlo para cumplir con el número de copias establecido, sin que el usuario detecte ninguna caida.

    Abrimos una segunda conexión SSH con el nodo Maestro y la dejamos escuchando los eventos del clúster:
    kubectl get events --watch --sort-by='.lastTimestamp'
    Comprobamos cuandos pods hay en ejecución y cuales son sus nombres (Nos fijamos tambien en el campo AGE):
    kubectl get pods
    Borramos el primer nodo de la lista (Comprobamos en el LOG de eventos que tenemos lanzado):
    kubectl delete pod **<POD_NAME>**
    Volvemos a confirmar el número de pods en ejecución y el tiempo que lleva cada uno levantado:
    kubectl get pods

    B) ACTUALIZACIÓN DE VERSIONES

    Imaginemos que queremos lanzar una nueva versión de una aplicación que ya tenemos desplegada. Simplemente debemos cambiar la imagen en el Deployment y volverlo a aplicar, para que nos genere un seguno Replicaset con la nueva versión.

    En primer lugar, vamos a editar nuestro deploy1.yaml, modificando la línea donde aparece la imagen de Nginx (pasaremos de la 1.21 a la 1.23); y también la línea donde aparece la causa del cambio (change-cause), que la modificaremos por "Actualización a nginx-1.23".

    nano deploy1.yaml
    Gurdamos los cambios y volvemos a aplicar el Deployment para que se actualice:
    kubectl apply -f deploy1.yaml
    Verificamos que se ha creado un segundo Replicaset (Revisión), con los pods de la nueva versión:
    kubectl get rs
    Verificamos que los pods que se están ejecutando ahora tienen la nueva versión (debemos ver la 1.23):
    kubectl describe pod | grep Image

    VOLVER A UNA VERSIÓN ANTERIOR

    También puede pasar que algo vaya mal durante la acutalización o que un servicio actualizado comienza a fallar o funcionar de una mnanera que no debe. En ese caso, vamos a ver como volver (downgrade) a una revisión anterior:

    kubectl rollout history deployment first-deployment-gx

    kubectl rollout undo deployment first-deployment-gx --to-revision=1

    kubectl get rs

    ASPECTO IMPORTANTE

    Por defecto, un Deployment almacena hasta 10 Replicaset (revisionHistoryLimit). Aunque ese valor se puede personalizar, es importante tener en cuenta que, al igual que un Rollout, cada Rollback genera un nuevo número de revisión en el historial, sin borrar los anteriores (respetando el revisionHistoryLimit, por defecto 10).

    C) ASOCIAR UN SERVICIO A NUESTRO DESPLIEGUE

    En Kubernetes, un Servicio es el tipo de objeto utilizado para exponer una aplicación de red, detrás de un único punto final externo, aún cuando esta se ejecute como uno o más Pods distribuidos entre los diferentes nodos del clúster.

    Esiten 4 tipos de servicios en Kubernetes y usaremos uno u otro dependiendo de nuestras necesidades:

    • ClusterIP: Expone el Servicio en una IP interna del clúster. Al elegir este valor, el Servicio solo será accesible desde dentro del clúster. Puede exponer el Servicio a Internet pública mediante un Ingress o un Gateway.
    • NodePort: Expone el Servicio en la IP de cada Nodo en un puerto estático (NodePort). Kubernetes configura una dirección IP de clúster, la misma que si hubieras solicitado un Servicio de type: ClusterIP.
    • LoadBalancer: Expone el servicio externamente mediante un balanceador de carga externo. Kubernetes no ofrece directamente un componente de balanceo de carga; debe proporcionarlo usted mismo.
    • ExternalName: Asigna el servicio al contenido del campo ExternalName (por ejemplo, al hostname api.foo.bar.example). Esta asignación configura el servidor DNS del clúster para que devuelva un registro CNAME con ese nombre de host externo.

    CREACIÓN Y LANZAMIENTO DEL SERVICE

    service1.yaml 
    apiVersion: v1
kind: Service
metadata:
  name: service-nginx-gx
spec:
  type: NodePort
  selector:
    app: nginx
  ports:
    - protocol: TCP
      port: 80
      targetPort: 80
      nodePort: 30080
    Creamos el manifiesto del servicio:
    nano service1.yaml
    Aplicamos el manifiesto en nuestro clúster:
    kubectl apply -f service1.yaml
    Comprobamos que el servicio se ha creado correctamente:
    kubectl get svc service-nginx-gx
    Verificamos que hay tantos endpoints asociados al servicio, como pods tiene nuestro Replicaset:
    kubectl get endpointslice -l kubernetes.io/service-name=service-nginx-gx

    COMPROBAR ACCESO AL SERVICIO

    Obtenemos la dirección IP de uno de los nodos (nos fijamos en la columna `INTERNAL-IP`):
    kubectl get nodes -o wide
    Verificamos el acceso via web desde un navegador:
    http://<IP-DEL-NODO>:30080

    D) ESCALADO DE RECURSOS

    Podemos escalar nuestro Deployment con más réplicas para soportar mayor carga de tráfico y garantizar la alta disponibilidad de tu aplicación. Ya que las replicas no solo nos dan redundancia, si no que cuando se genera un gran número de peticiones, el maestro las reparte entre las diferentes instancias (Pods) de nuestra aplicación que se estan ejecutando en paralelo, evitando así saturaciones en picos de tráfico.

    Ampliamos nuestro Replicaset a 4 copias:
    kubectl scale deployment first-deployment-gx --replicas=4

    E) ALMACENAMIENTO PERSISTENTE

    K3s incluye el provisionador Local Path, que crea PVC's ("Persistent Volume Claim") sobre almacenamiento local del nodo, y por defecto los datos se guardan en /var/lib/rancher/k3s/storage.

    Un PVC es como solicitud de almacenamiento persistente realizada por una aplicación para que un Pod pueda guardar datos de forma permanente, estos funcionan de forma similar a cómo un Pod solicita recursos de cómputo (CPU y memoria) a un nodo, es decir, el PVC actúa como un "ticket" o petición en la que se define cuánto espacio necesita y con qué permisos de acceso, sin tener que preocuparte por la infraestructura física que hay detrás.

    Al crear un PVC, Kubernetes busca un PV ("Persistent Volume") disponible, que es el espacio de almacenamiento real en el clúster, que cumpla con los requisitos solicitados (aprovisionamiento Estático) o crea uno automáticamente en ese momento mediante una StorageClass (aprovisionamiento Dinámico).

    A continuación, veremos un ejemplo de como asociar un volumen persistente a los pods de nuestro despliegue:

    Creamos el manifiesto para el PVC:
    nano volume1.yaml
    volume1.yaml 
    apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nginx-pvc
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: local-path
  resources:
    requests:
      storage: 500Mi
    Aplicamos el manifiesto en el clúster:
    kubectl apply -f volume1.yaml
    Dentro del manifiesto del Deployment, añadimos en las especificaciones del contenedor los datos referentes al volumen:
    spec:
  containers:
    - name: web
      image: nginx:1.23
      ports:
        - containerPort: 80
      volumeMounts:
        - name: nginx-volume-gx
          mountPath: /usr/share/nginx/html
  volumes:
    - name: nginx-volume-gx
      persistentVolumeClaim:
        claimName: nginx-pvc
    Aplicamos los cambios realizados:
    kubectl apply -f deploy1.yaml

    MONITORIZACIÓN DE RECURSOS VIRTUALIZADOS

    ¿QUÉ ES PROMETHEUS?

    Prometheus es un conjunto de herramientas de código abierto para la monitorización y notficación de alertas de sistemas.

    Prometheus recopila y almacena localmente métricas sobre aplicaciones y servicios en ejecución en datos de series de tiempo, es decir, la información de las métricas se almacena con la marca de tiempo en la que se registró, junto con pares clave-valor opcionales llamados etiquetas.

    Podemos visualizar estos datos mediante clientes API como Grafana.

    COMPONENTES PROMETHEUS

    El ecosistema Prometheus consta de múltiples componentes, muchos de los cuales son opcionales:

    • El servidor principal de Prometheus que recopila y almacena datos de series temporales.
    • Librerías de cliente para instrumentar el código de la aplicación.
    • Un push gateway para dar soporte a trabajos (jobs) de corta duración.
    • Exportadores de terceros para diferentes propósitos, como por ejemplo Grafana.
    • Un Alert Manager para gestionar alertas.
    • Herramientas de soporte variadas.

    ¿QUÉ ES GRAFANA?

    Grafana es una plataforma de código abierto de visualización, análisis y monitorización de datos; que permite transformar información numérica, métricas, registros (logs) y trazas procedentes de múltiples orígenes, en paneles gráficos (Dashboards) interactivos y fáciles de interpretar. Sus principales características son:

    • Paneles interactivos: Crea dashboards con gráficos de líneas, barras, tablas, medidores y mapas de calor.
    • Multi-fuente: Se conecta a bases de datos de series temporales, SQL y otras fuentes, sin encargarse de recolectar ni almacenar los datos por sí mismo.
    • Alertas y exploración: Permite configurar reglas de alerta y explorar datos en tiempo real para detectar fallos o picos de uso.

    INTEGRACIÓN CON PROMETHEUS

    Prometheus y Grafana cumplen roles complementarios, por un lado Prometheus recolecta y guarda las métricas en su base de datos de series temporales (mediante scraping periódicos a los targets o exporters del prometheus.yml); y por el otro, Grafana consulta esos datos y los representa de forma gráfica.

    Una forma muy resumida de explicar el flujo de datos entre ambos, puede ser la siguiente:

    1. Recolección en Prometheus: Prometheus consulta periódicamente los endpoints de los servicios o exporters (por ejemplo, CPU, memoria o peticiones por segundo) y guarda las series temporales.
    2. Añadir Data Source en Grafana: En la interfaz web de Grafana, se configura Prometheus como fuente de datos indicando la URL del servidor de Prometheus.
    3. Consultas con PromQL: Los paneles de Grafana envían consultas en PromQL (el lenguaje de consultas de Prometheus) para filtrar y calcular métricas.
    4. Visualización y alertas: Grafana dibuja los resultados en el panel y puede disparar alertas según los umbrales definidos.

    PRÁCTICA 2: MONITORIZANDO DEL CLÚSTER KUBERNETES

    ¿QUE ES HELM?

    Para realizar esta práctica, vamos a usar Helm, que es el gestor de paquetes de código abierto para Kubernetes, equivalente a herramientas como apt en Linux o npm en Node.js. Su función principal es simplificar la creación, instalación, configuración, actualización y rollback de aplicaciones complejas en un clúster de Kubernetes.

    En lugar de desplegar y gestionar manualmente varios archivos YAML dispersos (Deployment, Service, Ingress, etc.) usando kubectl, Helm agrupa todos los recursos necesarios para una aplicación en una sola unidad empaquetada.

    Los principales conceptos clave que implementa Helm, son:

    • Helm Chart: Es el paquete de Helm. Contiene la definición, la estructura y los archivos de configuración necesarios para ejecutar una aplicación en Kubernetes.
    • **Chart.yaml**: Su nombre hace referencia a un "mapa de navegación", ya que es un archivo que contiene los metadatos referentes a la aplicación empaquetada (nombre, versión, descripción).
    • **values.yaml**: Es el archivo que almacena los valores y variables configurables (número de réplicas, puertos, imágenes, contraseñas) para parametrizar el despliegue.
    • Plantillas (Templates): Son archivos YAML dinámicos dentro de la carpeta templates/ que se rellenan con los datos del archivo values.yaml.
    • Release (Versión): Es una instancia específica de un Chart ejecutándose en un clúster de Kubernetes. Un mismo Chart se puede instalar varias veces con distintas configuraciones.
    INSTALACIÓN DE HELM EN K3s

    Aunque K3s incluye internamente un controlador para desplegar manifiestos de Helm (HelmChart), no trae el comando **helm** preinstalado. Podemos instalarlo usando el script oficial recomendado en la documentación oficial de Helm:

    Script de instalación del CLI de Helm:
    curl -fsSL -o get\_helm.sh https://githubusercontent.com  
chmod 700 get\_helm.sh  
./get\_helm.sh

    Por defecto, Helm busca la configuración del clúster en ~/.kube/config, mientras que K3s la guarda en /etc/rancher/k3s/k3s.yaml. Por lo tando, debemos conectar Helm con nuestro clúster manualmente.

    Exportamos la ruta de K3s para que Helm pueda comunicarse con el clúster:
    export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
    Para hacer este cambio permanente en tu sesión de usuario (y evitar tener que usar `sudo` con cada instrucción):
    mkdir -p ~/.kube  
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config  
sudo chown $USER:$USER ~/.kube/config  
chmod 600 ~/.kube/config
    Comprobamos que la versión se muestra correctamente y que Helm tiene acceso al clúster listando los releases actuales:
    helm version  
helm list -A

    Objeto SECRET

    Un Secret en Kubernetes es un recurso para almacenar información sensible (contraseñas, tokens, claves SSH) de forma segura, separada del código y las configuraciones no confidenciales. Permitiendo que los Pods los consuman como archivos montados o variables de entorno sin exponerlos directamente.

    Creamos dos ficheros, uno para el nombre de usuario y otro para la contraseña. Y con ellos creamos un objeto secret donde se almacenará esa información sensible:

    echo -n 'admin' > ./admin-user

echo -n 'mipass123' > ./admin-password

kubectl create secret generic grafana-admin-credentials --from-file=./admin-user --from-file=admin-password -n monitoring

    kubectl describe secret -n monitoring grafana-admin-credentials

rm admin-user && rm admin-password

    Para el nombre de usuario:

    kubectl get secret -n monitoring grafana-admin-credentials -o jsonpath="{.data.admin-password}" | base64 --decode
